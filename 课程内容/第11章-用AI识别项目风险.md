# 第11章：用AI识别项目风险（不是简单的风险清单）

## 引言

上周和一位PM朋友聊天，他说："我每周都要做风险识别，但每次都是列一个风险清单：进度风险、质量风险、资源风险、技术风险。列完了，也不知道这些风险到底会不会发生，什么时候发生，影响有多大。等风险真的发生了，才发现清单里根本没有这个风险。"

这个问题太典型了。很多PM每天都要做风险识别，但效果往往不理想：风险清单是静态的，项目是动态的；风险识别是事后的，等风险发生了才发现；风险识别是表面的，只看到明显的风险，看不到潜在的风险。

这就像你有一个风险清单，但清单上的风险都是"可能发生"的，你不知道哪些真的会发生，什么时候发生。等风险真的发生了，你才发现清单里根本没有这个风险。

问题出在哪里？

不是风险清单不够详细，而是**我们没有从海量信息中识别潜在风险，没有在问题暴露之前识别风险信号，没有建立动态的风险识别系统**。风险识别的核心不是"列清单"，而是"模式识别"。PM需要的是从历史数据、当前状态、团队反馈中识别风险模式，在问题暴露之前识别风险信号，而不是等风险发生了再去总结。

这一章，我们要解决的就是这个问题。我们会学习如何用AI从海量信息中识别潜在风险，如何让AI学习历史风险案例，识别相似模式，如何让AI在问题暴露之前识别风险信号，如何构建AI风险识别系统。

这不是理论课，而是实战课。我们会用真实的游戏PM场景，让你看到如何从零开始构建AI风险识别系统，如何让AI成为你的风险预警助手。

## 本章术语速查表

| 术语 | 一句话解释 | 类比 |
|------|------------|------|
| **风险信号** | 表明风险可能发生的早期迹象 | 就像身体不舒服前的"小症状" |
| **风险模式** | 历史上反复出现的风险规律 | 就像"每次赶工都会出Bug"这种规律 |
| **领先指标** | 能预测未来问题的指标（如任务延期率） | 就像"体温升高"预示可能生病 |
| **滞后指标** | 反映已发生问题的指标（如Bug数量） | 就像"已经发烧了"说明已经生病 |
| **风险等级** | 根据影响和概率对风险的分级（高/中/低） | 就像医院的"急诊分级" |
| **预警阈值** | 触发预警的临界值（如延期率>20%） | 就像"体温超过38度要吃药" |
| **模式识别** | 从数据中发现规律和异常 | 就像医生从症状判断病因 |

> **关键认知**：风险识别的核心是"模式识别"，不是"列清单"。AI擅长从海量数据中识别模式，这正是它能帮助PM的地方。

## 11.1 风险识别的本质

在深入AI如何帮助PM识别风险之前，我们先搞清楚风险识别的本质是什么。

### 11.1.1 不是列清单：风险清单是静态的，项目是动态的

**传统方式：列风险清单**

**典型场景：**

项目PM小王每周都要做风险识别，他的方式是：
1. 打开风险清单模板
2. 列出常见的风险类型：进度风险、质量风险、资源风险、技术风险
3. 对每个风险类型，写一些"可能发生"的风险
4. 完成风险清单

**风险清单示例：**
```
项目风险清单：
1. 进度风险：可能延期
2. 质量风险：可能有Bug
3. 资源风险：可能资源不足
4. 技术风险：可能技术实现困难
```

**问题：**
- **静态的**：风险清单是固定的，不会随着项目变化而变化
- **表面的**：只看到明显的风险，看不到潜在的风险
- **事后的**：等风险发生了，才发现清单里没有这个风险
- **无用的**：不知道哪些风险真的会发生，什么时候发生

**为什么风险清单是静态的？**

**原因1：风险清单是模板化的**

风险清单通常是基于模板的，模板是固定的，不会随着项目变化而变化。比如：
- 模板说"可能有进度风险"，但不知道具体是什么进度风险
- 模板说"可能有质量风险"，但不知道具体是什么质量风险
- 模板说"可能有资源风险"，但不知道具体是什么资源风险

**原因2：风险清单是通用的**

风险清单通常是通用的，适用于所有项目，但每个项目的风险是不同的。比如：
- 二次元项目的风险可能是美术资源延期
- 技术项目的风险可能是技术方案未确定
- 运营项目的风险可能是用户流失

**原因3：风险清单是主观的**

风险清单通常是PM主观列出的，没有数据支撑，不知道哪些风险真的会发生。比如：
- PM觉得"可能有进度风险"，但没有数据支撑
- PM觉得"可能有质量风险"，但没有数据支撑
- PM觉得"可能有资源风险"，但没有数据支撑

**动态的风险识别：从数据中识别风险**

**正确方式：从数据中识别风险**

小王改用数据驱动的方式识别风险：
1. 收集项目数据：进度数据、质量数据、资源数据、团队反馈
2. 分析数据：识别数据中的异常和趋势
3. 识别风险：从数据中识别潜在风险
4. 持续监控：持续监控风险，及时调整

**数据驱动的风险识别示例：**
```
项目风险识别（基于数据）：
1. 进度风险：任务完成率从85%下降到75%，进度偏差从5%增加到15%
2. 质量风险：Bug数量从每周5个增加到每周12个，严重Bug比例从20%增加到40%
3. 资源风险：团队加班时长从平均5小时/周增加到平均12小时/周，出勤率从98%下降到95%
4. 技术风险：技术方案讨论时间从1周增加到3周，技术实现时间从2周增加到4周
```

**优势：**
- **动态的**：风险识别是动态的，随着项目数据变化而变化
- **深入的**：从数据中识别潜在风险，不只是表面的风险
- **先行的**：在问题暴露之前识别风险信号
- **有用的**：知道哪些风险真的会发生，什么时候发生

### 11.1.2 是模式识别：从历史数据、当前状态、团队反馈中识别模式

**什么是模式识别？**

模式识别是指从数据中识别出规律和模式。在风险识别中，模式识别是指：
- **历史模式**：从历史风险案例中识别风险模式
- **当前模式**：从当前项目数据中识别风险模式
- **反馈模式**：从团队反馈中识别风险模式

**历史模式：从历史风险案例中识别风险模式**

**典型场景：**

资深PM小李负责的项目，历史上经常出现以下风险：
- **风险1**：美术资源延期（出现3次）
  - 模式：美术资源制作进度从80%开始下降，团队反馈"资源不足"
  - 信号：进度下降、团队反馈
- **风险2**：技术方案未确定（出现2次）
  - 模式：技术方案讨论时间超过2周，团队反馈"方案不确定"
  - 信号：讨论时间延长、团队反馈
- **风险3**：版本延期（出现1次）
  - 模式：任务完成率连续2周下降，进度偏差超过10%
  - 信号：完成率下降、进度偏差

**如何识别历史模式？**

**第一步：收集历史风险案例**

收集历史上发生的风险案例，包括：
- 风险描述：什么风险？
- 风险信号：什么信号预示风险？
- 风险影响：风险对项目的影响？
- 风险应对：如何应对风险？

**第二步：分析风险模式**

分析历史风险案例，识别风险模式：
- 哪些信号预示哪些风险？
- 风险发生的规律是什么？
- 风险的影响是什么？

**第三步：建立风险模式库**

建立风险模式库，记录：
- 风险类型：什么类型的风险？
- 风险信号：什么信号预示风险？
- 风险模式：风险的规律是什么？

**当前模式：从当前项目数据中识别风险模式**

**典型场景：**

负责外包资源管理的PM小张，当前项目数据如下：
- **进度数据**：任务完成率从85%下降到75%，进度偏差从5%增加到15%
- **质量数据**：Bug数量从每周5个增加到每周12个，严重Bug比例从20%增加到40%
- **资源数据**：团队加班时长从平均5小时/周增加到平均12小时/周，出勤率从98%下降到95%

**如何识别当前模式？**

**第一步：收集当前项目数据**

收集当前项目的各种数据：
- 进度数据：任务完成率、进度偏差、里程碑达成情况
- 质量数据：Bug数量、Bug等级、测试通过率
- 资源数据：团队出勤率、加班时长、资源利用率
- 技术数据：技术方案讨论时间、技术实现时间

**第二步：分析数据异常**

分析数据中的异常和趋势：
- 哪些数据异常？异常的原因是什么？
- 哪些数据趋势？趋势的方向是什么？
- 哪些数据关联？关联的关系是什么？

**第三步：识别风险模式**

从数据异常和趋势中识别风险模式：
- 哪些数据异常预示哪些风险？
- 哪些数据趋势预示哪些风险？
- 哪些数据关联预示哪些风险？

**反馈模式：从团队反馈中识别风险模式**

**典型场景：**

PM小陈负责的项目，团队反馈如下：
- **站会反馈**："资源不足，进度可能延期"
- **周会反馈**："技术方案不确定，实现可能困难"
- **私下反馈**："团队状态不好，可能有人员风险"

**如何识别反馈模式？**

**第一步：收集团队反馈**

收集团队的各种反馈：
- 站会反馈：每日站会的反馈
- 周会反馈：每周例会的反馈
- 私下反馈：私下沟通的反馈
- 文档反馈：文档中的反馈

**第二步：分析反馈内容**

分析反馈的内容和语气：
- 反馈的内容是什么？反馈的语气是什么？
- 反馈的频率是什么？反馈的趋势是什么？
- 反馈的关联是什么？反馈的模式是什么？

**第三步：识别风险模式**

从反馈内容和语气中识别风险模式：
- 哪些反馈预示哪些风险？
- 哪些反馈频率预示哪些风险？
- 哪些反馈趋势预示哪些风险？

### 11.1.3 是先行指标：在问题暴露之前识别风险信号

**什么是先行指标？**

先行指标是指能够提前预示问题发生的指标。在风险识别中，先行指标是指：
- **进度先行指标**：能够提前预示进度问题的指标
- **质量先行指标**：能够提前预示质量问题的指标
- **资源先行指标**：能够提前预示资源问题的指标
- **技术先行指标**：能够提前预示技术问题的指标

**进度先行指标：能够提前预示进度问题的指标**

**典型场景：**

小王负责的项目，进度数据如下：
- **第1周**：任务完成率85%，进度偏差5%
- **第2周**：任务完成率80%，进度偏差8%
- **第3周**：任务完成率75%，进度偏差12%
- **第4周**：任务完成率70%，进度偏差18%（问题暴露）

**先行指标：**
- **任务完成率下降**：从85%下降到75%，下降10个百分点
- **进度偏差增加**：从5%增加到12%，增加7个百分点
- **信号时间**：第3周（问题暴露前1周）

**如何识别进度先行指标？**

**第一步：收集进度数据**

收集项目的进度数据：
- 任务完成率：每周的任务完成率
- 进度偏差：每周的进度偏差
- 里程碑达成情况：关键里程碑的达成情况

**第二步：分析数据趋势**

分析数据的趋势和变化：
- 任务完成率是否下降？下降的幅度是多少？
- 进度偏差是否增加？增加的幅度是多少？
- 里程碑是否可能延期？延期的可能性是多少？

**第三步：识别先行指标**

从数据趋势中识别先行指标：
- 哪些指标能够提前预示进度问题？
- 这些指标的阈值是什么？
- 这些指标的预警时间是什么？

**质量先行指标：能够提前预示质量问题的指标**

**典型场景：**

小李负责的项目，质量数据如下：
- **第1周**：Bug数量5个，严重Bug比例20%
- **第2周**：Bug数量8个，严重Bug比例25%
- **第3周**：Bug数量12个，严重Bug比例35%
- **第4周**：Bug数量18个，严重Bug比例45%（问题暴露）

**先行指标：**
- **Bug数量增加**：从5个增加到12个，增加140%
- **严重Bug比例增加**：从20%增加到35%，增加15个百分点
- **信号时间**：第3周（问题暴露前1周）

**如何识别质量先行指标？**

**第一步：收集质量数据**

收集项目的质量数据：
- Bug数量：每周的Bug数量
- Bug等级：Bug的等级分布
- 测试通过率：测试的通过率
- 返工率：返工的任务比例

**第二步：分析数据趋势**

分析数据的趋势和变化：
- Bug数量是否增加？增加的幅度是多少？
- 严重Bug比例是否增加？增加的幅度是多少？
- 测试通过率是否下降？下降的幅度是多少？

**第三步：识别先行指标**

从数据趋势中识别先行指标：
- 哪些指标能够提前预示质量问题？
- 这些指标的阈值是什么？
- 这些指标的预警时间是什么？

**资源先行指标：能够提前预示资源问题的指标**

**典型场景：**

小张负责的项目，资源数据如下：
- **第1周**：团队出勤率98%，加班时长5小时/周
- **第2周**：团队出勤率96%，加班时长8小时/周

- **信号时间**：第3周（问题暴露前1周）

**如何识别资源先行指标？**

**第一步：收集资源数据**

收集项目的资源数据：
- 团队出勤率：每周的团队出勤率
- 加班时长：每周的平均加班时长
- 资源利用率：资源的利用率
- 资源缺口：资源的缺口情况

**第二步：分析数据趋势**

分析数据的趋势和变化：
- 出勤率是否下降？下降的幅度是多少？
- 加班时长是否增加？增加的幅度是多少？
- 资源利用率是否过高？过高的程度是多少？

**第三步：识别先行指标**

从数据趋势中识别先行指标：
- 哪些指标能够提前预示资源问题？

## 11.2 AI风险识别的核心思路

了解了风险识别的本质，接下来我们要学习如何用AI识别风险。

### 11.2.1 数据源：进度数据、质量数据、资源数据、团队反馈

**为什么要收集多源数据？**

风险信号可能出现在不同的数据源中：
- **进度数据**：任务完成率、进度偏差、里程碑达成情况
- **质量数据**：Bug数量、Bug等级、测试通过率
- **资源数据**：人力配置、外包进度、团队出勤率
- **团队反馈**：站会反馈、周会反馈、私下反馈

如果只从一个数据源识别风险，可能会遗漏其他数据源中的风险信号。

> **注意**：研发阶段的风险识别，数据源主要是内部研发数据。如果是已上线项目，还需要关注运营数据（用户数据、留存数据、付费数据等），但这通常是运营团队的职责，PM更多是配合和协调，而不是主导。

**团队反馈：站会反馈、周会反馈、私下反馈**

**典型场景：**

小李负责的项目，团队反馈如下：
- **站会反馈**："资源不足，进度可能延期"
- **周会反馈**："技术方案不确定，实现可能困难"
- **私下反馈**："团队状态不好，可能有人员风险"

**风险信号：**
- **资源风险**：站会反馈"资源不足"，可能预示资源风险
- **技术风险**：周会反馈"技术方案不确定"，可能预示技术风险
- **人员风险**：私下反馈"团队状态不好"，可能预示人员风险

**如何收集团队反馈？**

**方式1：从会议记录收集**

从会议记录中收集团队反馈：
- 站会记录：每日站会的反馈
- 周会记录：每周例会的反馈
- 评审会记录：评审会的反馈

**方式2：从沟通工具收集**

从沟通工具中收集团队反馈：
- 钉钉/企微：团队群聊的反馈
- 邮件：邮件中的反馈
- 文档：文档中的反馈

### 11.2.3 预警机制：当检测到风险信号时，自动提醒PM

**为什么要建立预警机制？**

风险信号可能随时出现，如果PM不能及时发现，可能会错过最佳应对时机。建立预警机制，可以：
- **及时提醒**：当检测到风险信号时，自动提醒PM
- **持续监控**：持续监控项目数据，及时发现风险信号
- **自动预警**：自动生成风险预警报告，不需要PM手动操作

**如何建立预警机制？**

**第一步：定义预警规则**

### 11.3.1 第一步：建立风险案例库（历史风险案例）

**为什么要建立风险案例库？**

风险案例库是AI学习的基础，包含了丰富的风险模式信息。如果没有风险案例库，AI就无法学习历史风险案例，无法识别相似模式。

**如何建立风险案例库？**

**第一步：收集历史风险案例**

收集历史上发生的风险案例，包括：
- **项目信息**：项目类型、项目阶段、团队规模
- **风险信息**：风险描述、风险类型、风险等级
- **风险信号**：什么信号预示风险？
- **风险模式**：风险的规律是什么？
- **风险影响**：风险对项目的影响？
- **风险应对**：如何应对风险？
- **发生时间**：风险发生的时间

## 11.4 案例：用AI识别美术外包延期风险

了解了如何构建AI风险识别系统，接下来我们看一个完整的案例。

### 案例：某修仙项目PM用AI识别美术外包延期风险

**背景：**
- 项目类型：修仙/仙侠品类3D游戏
- 团队规模：30人（内部研发）+ 外包合作方（3家美术外包公司）
- 项目阶段：开发中期，正在进行角色和场景美术资源的批量制作
- 问题：美术外包资源占整体美术工作量的60%，但外包进度难以监控，历史上多次出现延期

**问题：**
- 美术外包的交付节点分散，PM很难及时掌握真实进度
- 外包团队的沟通频率低（每周1次），等发现问题时往往已经来不及调整
- 历史上有2次因为外包延期导致版本延期的情况，制作人对此非常关注
- PM需要在外包延期风险暴露之前，提前识别风险信号

**处理方式：**

**第一步：建立外包风险案例库**

PM梳理了历史上的外包延期案例，建立了风险案例库：

```
风险案例库：

案例1：角色外包A公司延期风险（2024年8月）
- 风险描述：角色模型外包延期2周，影响后续绑定和动画制作
- 风险信号：
  - 进度信号：周进度汇报连续2周显示"进行中"但无阶段性交付物
  - 反馈信号：外包方开始频繁询问"验收标准是否可以调整"
  - 沟通信号：外包方响应邮件的时间从平均1天延长到3天
- 风险影响：版本延期5天，PM协调内部主美安排人员加班补进度

案例2：场景外包B公司延期风险（2024年10月）
- 风险描述：场景资源外包延期1周，影响版本整体进度
- 风险信号：
  - 进度信号：任务完成率从前2周的85%下降到65%
  - 质量信号：返工率从10%上升到30%
  - 反馈信号：外包方反馈"人手不足，需要协调"
- 风险影响：版本延期3天，PM紧急协调另一家外包公司支援
```

**第二步：让AI学习外包风险案例**

PM让AI学习外包风险案例，识别风险模式：

```
你是一名游戏项目经理，请帮我学习美术外包的历史风险案例，识别风险模式。

【风险案例库】
[粘贴上述外包风险案例]

【学习任务】
1. 分析每个外包延期案例的风险信号
2. 识别外包延期的风险模式（进度信号、沟通信号、质量信号）
3. 总结外包延期的先行指标
4. 建立外包风险模式库

请按照以下结构输出：
1. 【风险信号分析】[分析每个案例的风险信号]
2. 【风险模式识别】[外包延期的典型模式]
3. 【先行指标总结】[哪些信号可以提前预警]
4. 【风险模式库】[建立外包风险模式库]
```

AI生成了外包风险模式库：
- **进度下滑模式**：周进度完成率连续2周下降超过10%
- **沟通异常模式**：响应时间延长、频繁询问验收标准调整
- **质量波动模式**：返工率连续上升、一次通过率下降

**第三步：定义外包风险识别规则**

PM根据风险模式库，定义了外包风险识别规则：

```
外包风险识别规则：

1. 进度风险（高风险）：
   - 周进度完成率连续2周下降超过10个百分点
   - 未按时提交阶段性交付物超过3天

2. 沟通风险（中风险）：
   - 邮件/消息响应时间从平均1天延长到3天以上
   - 频繁询问验收标准调整（1周内超过2次）

3. 质量风险（中风险）：
   - 返工率从正常水平（<15%）上升到25%以上
   - 一次验收通过率下降超过20%

4. 资源风险（高风险）：
   - 外包方主动反馈"人手不足"或"需要协调"
   - 关键人员（主美、负责人）更换
```

**第四步：让AI持续监控外包数据**

PM每周收集外包数据，让AI监控风险：

```
你是一名游戏项目经理，请帮我监控美术外包风险。

Components：需要监控进度数据、沟通数据、质量数据，识别风险信号
Criteria：风险信号要具体可追溯；要区分风险等级；要提供可执行的应对建议

【本周外包数据】
外包公司A（角色模型）：
- 本周计划交付：5个角色模型
- 实际交付：3个（完成率60%，上周是85%）
- 返工率：25%（上周15%）
- 沟通记录：本周询问了2次"这个角色的盔甲细节是否可以简化"

外包公司B（场景资源）：
- 本周计划交付：8个场景模块
- 实际交付：7个（完成率87.5%）
- 返工率：12%（正常范围）
- 沟通记录：正常，响应及时

外包公司C（特效资源）：
- 本周计划交付：10个技能特效
- 实际交付：10个（完成率100%）
- 返工率：8%
- 沟通记录：正常

【风险识别规则】
[粘贴外包风险识别规则]

请识别风险并输出预警报告。
```

**第五步：AI识别出外包A公司风险**

AI识别出外包A公司存在延期风险：
- **高风险**：进度完成率从85%下降到60%，下降25个百分点，触发进度风险规则
- **中风险**：返工率从15%上升到25%，触发质量风险规则
- **中风险**：1周内2次询问验收标准调整，触发沟通风险规则

AI预警："外包公司A存在延期风险，建议立即与外包方沟通确认原因，预计可能影响后续2周的版本进度"

**第六步：PM及时干预**

PM收到预警后，立即与外包A公司负责人通话，了解到：
- 原因：外包方的主美临时被抽调到其他项目，导致产能下降
- 预计影响：如果不干预，可能延期5-7天

PM采取应对措施：
1. 与外包方负责人沟通，明确要求在3天内恢复主美配置，否则评估更换供应商
2. 与内部主美沟通，协调内部美术团队承接2个复杂度较低的角色（PM负责协调，主美确认可行性和人员安排）
3. 提前通知后续环节负责人（绑定组长、动画组长），同步可能的进度调整，让他们有时间准备应对方案

**第七步：PM审核和优化预警系统**

PM复盘发现AI预警的时机比人工发现提前了1周，避免了版本延期。PM优化了预警系统：
- 增加"关键人员变动"作为高优先级风险信号
- 将"询问验收标准调整"的阈值从2次调整为1次

**结果：**
- **预警时机**：从"延期已经发生"到"延期前1周预警"
- **应对效果**：成功避免外包延期影响版本进度
- **效率提升**：外包监控从"每周人工检查"到"AI自动预警+PM审核"

**复盘：**
这个案例的关键启示：
1. **外包风险有明显的先行指标**：进度下滑、沟通异常、质量波动都是外包延期的先行信号
2. **AI可以从历史案例中学习风险模式**：让AI学习历史外包延期案例，能够识别相似的风险模式
3. **预警的价值在于争取应对时间**：提前1周预警，PM就有时间协调资源、调整计划
4. **PM需要持续优化预警规则**：根据实际情况调整风险阈值，让预警越来越准

## AI风险识别的边界和局限

AI风险识别是一个强大的工具，但它有明确的边界和局限。了解这些边界，能帮你更好地使用它。

### PM在风险识别中的职责边界

在使用AI辅助风险识别时，PM需要明确自己的职责边界：

| PM应该做的 | PM不应该做的 |
|-----------|-------------|
| **识别和预警风险** | 替其他职能诊断具体问题原因 |
| **收集和整理数据** | 亲自去写代码、做测试、画原型 |
| **协调资源和推动决策** | 直接指挥其他职能如何执行工作 |
| **跟踪应对措施落地** | 替其他职能承担执行责任 |
| **向上汇报风险和建议** | 越过职能负责人直接做技术/业务决策 |

> **关键认知**：PM的核心价值是"让正确的人在正确的时间做正确的事"，而不是"自己把所有事情都做了"。在风险识别中，PM负责发现风险、传递信息、协调资源、推动决策，但具体的技术判断、业务决策、执行落地应该由相应的职能负责人来完成。

### AI风险识别能做什么？

| 能力 | 说明 | 举例 |
|------|------|------|
| **模式识别** | 从历史数据中识别风险模式 | "每次美术外包延期，都是因为沟通不及时" |
| **异常检测** | 发现数据中的异常 | "本周任务延期率突然从10%升到30%" |
| **趋势预测** | 根据趋势预测风险 | "按当前进度，里程碑可能延期2周" |
| **信号关联** | 关联多个信号，识别复合风险 | "延期率上升+加班增加+Bug增加=赶工风险" |

### AI风险识别不能做什么？

| 局限 | 说明 | 应对方法 |
|------|------|----------|
| **不能识别全新风险** | AI只能识别历史上出现过的风险模式 | 定期更新风险案例库，人工补充新风险 |
| **不能判断风险严重性** | AI可以提示风险，但严重性需要人判断 | AI提供数据，PM做判断 |
| **不能替你做决策** | 是否采取行动、采取什么行动，需要人决策 | AI提供建议，PM做决策 |
| **不能处理模糊信息** | 团队的"感觉"、"氛围"等模糊信息，AI难以处理 | 结合人的观察和AI的分析 |
| **不能保证100%准确** | AI可能误报（没风险说有）或漏报（有风险没发现） | 建立人工复核机制 |

### 使用AI风险识别的最佳实践

| 实践 | 说明 |
|------|------|
| **AI识别 + 人工复核** | AI负责初筛，人负责确认和决策 |
| **定期更新风险案例库** | 每次风险发生后，更新案例库，让AI学习 |
| **设置合理的预警阈值** | 阈值太低会误报太多，阈值太高会漏报 |
| **结合多个数据源** | 单一数据源可能有偏差，多数据源交叉验证 |
| **保持对AI的怀疑** | AI说"没有风险"不代表真的没有风险 |

> **关键认知**：AI是风险识别的"助手"，不是"替代者"。最终的风险判断和决策，必须由PM来做。

## 本章小结

这一章我们学习了如何用AI识别项目风险。

**核心要点：**

1. **风险识别的本质**
   - 不是列清单：风险清单是静态的，项目是动态的
   - 是模式识别：从历史数据、当前状态、团队反馈中识别模式
   - 是先行指标：在问题暴露之前识别风险信号

2. **AI风险识别的核心思路**
   - 数据源：进度数据、质量数据、资源数据、团队反馈（研发阶段聚焦内部数据）
   - 识别模式：AI学习历史风险案例，识别相似模式
   - 预警机制：当检测到风险信号时，自动提醒PM

3. **构建AI风险识别系统**
   - 第一步：建立风险案例库（历史风险案例）
   - 第二步：定义风险识别规则（什么信号代表什么风险）
   - 第三步：让AI持续监控和识别
   - 第四步：AI自动生成风险预警报告

**关键启示：**

AI可以学习历史风险案例，识别相似模式，从海量信息中识别潜在风险，在问题暴露之前识别风险信号。但AI不能替代PM的判断。PM需要：
- 建立风险案例库，AI才能学习
- 定义风险识别规则，AI才能识别
- 审核识别结果，确保质量
- 优化识别方法，越用越好

**职责边界意识：**

在风险识别和应对过程中，PM要始终保持职责边界意识：
- **PM的核心职责**：识别风险、传递信息、协调资源、推动决策、跟踪进度、向上汇报
- **PM不应该做的**：替其他职能诊断具体技术问题、直接执行技术工作或业务工作、越过职能负责人做决策
- **PM的价值体现**：让正确的人在正确的时间做正确的事，而不是自己把所有事情都做了
